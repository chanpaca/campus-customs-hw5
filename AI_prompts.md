- **Critique / Notes:** "Query strictly without hallucinating" was the only part of the prompt stated as an intention rather than a mechanism, so it had to be turned into something enforceable — the connection opens with SQLite's `mode=ro` flag (an `UPDATE` through it raises `attempt to write a readonly database`), missing rows return `found: false` plus the values that do exist instead of a plausible guess, and every date judgement resolves against `desk.date_today` rather than the wall clock so "overdue" cannot drift; the prompt also did not mention the environment, and the machine-wide FastMCP install turns out to be broken (`ModuleNotFoundError: uncalled_for`), so the server was built and verified against the working FastMCP 4.0.10 in `mcp_servers/.venv/`, which is what `.mcp.json` will need to point at in Problem 4. ## Problem 7 — Backend Routes

- **Initial Prompt:** "build Problem 7: the FastAPI backend routes in backend/main.py. We need routes that our upcoming React frontend will call: 1. GET /api/tickets: return all three tickets with their fields and status (open vs resolved). 2. POST /api/tickets/{id}/run: trigger the multi-agent team on the selected ticket. 3. GET /api/events: return recent agent activity (agent dialog, tool calls, delegations, timestamps) so the frontend live-updates. 4. POST /api/payments/approve: human approval endpoint — agents can only prepare payment vouchers; this route is what actually records payment in payments and deducts cash from checking in cash_accounts. 5. GET /api/cash: return the current checking balance from cash_accounts. 6. POST /api/reset: reset data/campus_customs_new.db back to original values from data/campus_customs.db for fresh runs. 7. Add CORS middleware allowing http://localhost:5173 (our Vite frontend origin). 8. In output/harness.md, add an API Routes section listing each endpoint URL and what it does in one concise line."
- **Follow-up Prompt:** "Test starting the FastAPI server using `uvicorn main:app --reload --port 8000`. Test each endpoint with a quick test script or curl to make sure the reset route properly restores the database file and the payment approval route properly updates cash_accounts."
- **Critique / Notes:** Two design questions the prompt left open had to be decided rather than guessed — a ticket run takes far longer than an HTTP request should block, so `/api/tickets/{id}/run` starts the team in the background and returns a `run_id` (with `wait: true` and a `/api/runs/{run_id}` poll route added for synchronous use), and `/api/events` gained `since_seq` filtering so the live feed can poll for deltas instead of re-reading the whole trail every second; a refused payment also returns `400` rather than `500`, because a guardrail firing is the system working. Port 8001 from the launch config was already held by another session's server, so the API runs on 8010, and CORS allows the `:5174` pair alongside the specified `:5173` because another project in this repo holds 5173. Every route was exercised against a running server, including the full cash path — a human approval moved $3,400.00 → $2,560.00 and marked invoice 501 paid, the repeat was refused as a double-payment, and `/api/reset` restored the working database byte-identical to the seed. The follow-up caught a real defect: the requested command `uvicorn main:app` failed with `ModuleNotFoundError: No module named 'backend'`, because launching from inside `backend/` puts that directory on `sys.path` but not the project root, so the module's own `backend.*` imports could not resolve — `main.py` now inserts the project root at import time and works under both launch styles, and `backend/test_api.py` was added as a repeatable 34-check suite (all passing) that asserts the state-changing routes rather than eyeballing them.
